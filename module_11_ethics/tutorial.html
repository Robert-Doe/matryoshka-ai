1 · A 93%-accurate model that discriminates

py module_11_ethics\bias_audit.py

🛡 The harm hides in the aggregate

GroupAccuracyApproval rateFalse-reject rate
A~93%~50%~9%
B~93%~29%~15%

Same overall accuracy, very different treatment — the model faithfully learned bias baked into historical labels. Dropping the sensitive feature doesn't fix it (other features are proxies). Try it.

2 · "Fair" is many incompatible things

py module_11_ethics\fairness_metrics.py

You must choose a definition

  • Demographic parity — equal approval rate.
  • Equal opportunity — equal true-positive rate (equal treatment of the qualified).
  • Predictive parity — a "yes" means the same for each group.

When base rates differ you generally cannot satisfy all three (a theorem, not a bug). So "is it fair?" has no purely technical answer — you pick the definition that fits the decision and defend it.

3 · The safety map & the red-team tool

Read alignment_notes.md — the conceptual map (specification gaming, RLHF, interpretability, evals) — and red_team_checklist.md, a practical checklist you run on any model. Both connect each safety axis back to a mechanism you already built (memorization, adversarial examples, poisoning, prompt injection).

🛡 This is your bridge, not a detour

A fairness/safety audit is threat modeling: assume adversaries, enumerate attack surfaces, don't trust input, defend in depth. Adversarial ML, prompt injection, red-teaming, and evals are your security instincts applied to models. You're porting a discipline you already own.
